## 8. 🧪 Evaluating Your Agents

This design declares no evaluation suites. Surla verifies a commit with an evaluator suite that is a separate Go module: an `eval/` module in the layout `surla init` creates, or the suite named by the server's verification settings the user stored with `surla verification set`. When a build runs with a test writer (without stored verification settings), `eval/` (`eval/design/` included) belongs to the test writer. Surla regenerates `eval/gen/` when the writer reads an unread assignment and at each report; after changing `eval/design/`, the writer reports to have Surla generate it again, or runs `surla gen -dir eval` from a shell. The writer runs every Go command with `GOWORK=off`, leaves Surla's Story table unchanged and does not commit: Surla commits the tests it accepts. The builder leaves this test module untouched. Outside such a build, the builder can regenerate it with `generate_code` and `target: "eval"` after its design changes. Without stored verification settings, `verify_change` runs the tests Surla accepted for the user's build of the change, at the commit where it accepted them. With stored verification settings, it runs the suite commit named in them, which the server reads when Surla starts, so after you commit an edited suite, ask the user to store that commit with `surla verification set` and to run `surla stop`, then `surla`.
