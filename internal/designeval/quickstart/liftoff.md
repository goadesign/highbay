## 2. 🚀 The 3-Step Liftoff: Your First Agent Run

Use the MCP tools on the Surla project server for this project's generation, build checks and verification:

1. The guide edits the next design only in its draft, refreshes it and proposes a revision for the user to adopt. The builder reads its assignment before working in its own project copy, then calls `generate_code`: Surla writes the agreed design into `design/` and regenerates `gen/` and this guide. The builder edits neither `design/` nor `gen/`; a design change goes back to the guide. When a build runs with a test writer (without stored verification settings), `eval/` (`eval/design/` included) belongs to the test writer. Surla regenerates `eval/gen/` when the writer reads an unread assignment and at each report; after changing `eval/design/`, the writer calls `report_tests_finished` to regenerate it, or runs `surla gen -dir eval` from a shell. The writer prefixes every Go command with `GOWORK=off` and never commits; Surla commits accepted tests. Outside such a build, the builder can regenerate `eval/` with `generate_code` and `target: "eval"`. An operator can regenerate a local module with `surla gen -dir <module>` from a shell.
2. The builder implements the agreed design in the hand-written code and calls `check_project` to build and test uncommitted files in its working copy. When its message reports a missing `go.sum` or `go.work.sum` entry or a `go.mod` update, the builder calls `update_dependencies` and checks again; `read_check_output` returns the captured output. When the assignment's `gowork_off` is true, prefix every Go command in this copy with `GOWORK=off`.
3. The builder commits on the branch checked out in its copy. Every Surla project server has verification configured: `verify_change` runs, against the commit, the tests Surla accepted for the user's build of the change's revision or, with verification settings the user stored with `surla verification set`, their evaluator suite. The builder passes the commit as `candidate_commit` with the `change_id` and `request_revision` of the confirmed Change Card (the guide proposes the card with `propose_change`, and the user confirms it on the views page); without stored verification settings, `verify_change` is refused until the user has built that revision and Surla has accepted the test writer's tests, as the builder's assignment shows. It returns a `run_id`; call `get_verification` with it to read the run's state and result. `start_live_target` takes the confirmed change's `change_id` and a `candidate_commit`, so `draft_override` can try prompt wording on that live copy. Without stored verification settings, both tools use the tests Surla accepted for the change's current build; choose a model in the Live target view before starting the target. With stored settings, the evaluator in the stored verification settings starts it without a build or accepted test-writer tests.

Surla does not run `goa example`. When this project contains the files it scaffolds, such as `cmd/<service>/main.go`, `internal/agents/<service>/bootstrap/bootstrap.go` and `internal/agents/<agent>/planner/planner.go`, they are yours to edit, and the rest of this part explains what they do.


The test writer reports `coverage_statements` with `report_tests_finished`: When you call report_tests_finished, include coverage_statements. For each scenario whose coverage you state, give its exact scenario ID, question_ids from this assignment's answers[].id, example_ids from examples[].id, and an explanation of the interaction or assertion that exercises them. Use an empty array when you state none; Surla will show Not stated. These are your statements, not Surla's judgment of what your tests assert. The tests must still hold the service to every confirmed answer, example and preserved behavior. Surla validates supplied references while checking your report. Read get_test_writer_assignment for the verdict and the statements you submitted; correct any stated-reference findings and report again. Do not commit: Surla records the tests it accepts.
